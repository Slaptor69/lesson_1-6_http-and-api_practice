# Frontend: клиент для API

Страница и оформление уже готовы. В `script.js` подготовлены DOM-элементы и две вспомогательные функции. Ваша задача — соединить интерфейс с API.

Перед началом убедитесь, что:

- `npm run dev` продолжает работать в папке `backend`;
- `http://localhost:3000/applications` открывается в браузере;
- `frontend/index.html` запущен через Live Server;
- открыты Console и Network.

## Блок 2. Получение данных через `fetch` — 10 минут

**Цель:** пройти путь `fetch → Response → JSON` и увидеть данные в Console.

Работайте в функции `loadApplications`.

### 2.1 — Выполните GET-запрос

Вместо `TODO 2.1` вызовите `fetch(API_URL)` и дождитесь результата:

```js
const response = await fetch(API_URL)
```

Передавать настройки не нужно: без второго аргумента `fetch` выполняет `GET`.

### 2.2 — Преобразуйте тело ответа

Вместо `TODO 2.2` вызовите метод `json` у объекта `Response`:

```js
const applications = await response.json()
```

Здесь нужен второй `await`: чтение тела ответа тоже асинхронно.

### 2.3 — Сравните ответ и данные

Выведите в Console:

```js
console.log("Response:", response)
console.log("Applications:", applications)
```

Найдите различие:

- `response` содержит сведения об HTTP-ответе;
- `applications` содержит массив из `db.json`.

Откройте Network, выберите запрос `applications` и найдите:

1. Request Method;
2. Request URL;
3. Status Code;
4. вкладку Response.

**Промежуточный результат:** в Console виден массив. Страница пока может оставаться в состоянии загрузки — рендер появится в следующем блоке.

### Быстрая проверка блока 2

- запрос имеет метод `GET`;
- Network показывает статус `200`;
- `response` и массив — разные значения;
- в массиве столько объектов, сколько сейчас находится в `db.json`;
- в Console нет `Promise` вместо данных.

## Блок 3. Рендер и состояния интерфейса — 10 минут

**Цель:** показать данные пользователю и корректно обработать пустой массив.

### 3.1 — Очистите старый результат

В начале `renderApplications` очистите список:

```js
applicationList.replaceChildren()
```

Это важно для кнопки «Обновить»: повторный запрос не должен дублировать карточки.

### 3.2 — Обработайте пустой массив

Если `applications.length === 0`:

1. вызовите `setListState("empty", "API вернул пустой массив")`;
2. завершите функцию через `return`.

Пустой ответ — успешный результат запроса, а не ошибка.

### 3.3 — Создайте карточки

Переберите массив через `forEach`. Для каждого объекта:

1. вызовите готовую функцию `createApplicationCard(application)`;
2. добавьте результат в `applicationList` методом `append`.

### 3.4 — Покажите успешное состояние

После цикла вызовите:

```js
setListState("success", `Получено заявок: ${applications.length}`)
```

### 3.5 — Свяжите загрузку и рендер

После получения массива в `loadApplications` вызовите:

```js
renderApplications(applications)
```

**Видимый результат:** вместо вечной загрузки появляются карточки из `db.json`.

### Контроль пустого состояния

1. Не останавливая сервер, временно замените массив `applications` в `db.json` на `[]`.
2. Нажмите «Обновить» на странице.
3. Убедитесь, что появился блок «Заявок пока нет».
4. Верните исходные объекты через отмену изменения в редакторе.

### Быстрая проверка блока 3

- повторное обновление не дублирует карточки;
- количество карточек совпадает с длиной массива;
- данные карточек пришли с API, а не записаны в HTML;
- пустой массив показывает отдельное состояние;
- после возврата данных список снова отображается.

## Блок 4. HTTP-ошибки и Network — 10 минут

**Цель:** отличить сетевую ошибку от HTTP-ответа и не оставлять интерфейс в неопределенном состоянии.

### 4.1 — Проверьте `response.ok`

Сразу после `fetch` добавьте проверку:

```js
if (!response.ok) {
  throw new Error(`HTTP ${response.status}`)
}
```

`fetch` не обязан переходить в `catch` при статусе `404`. Поэтому HTTP-статус проверяется отдельно.

### 4.2 — Покажите ошибку пользователю

В `catch` вызовите:

```js
setListState("error", "Не удалось загрузить заявки. Проверьте API и повторите запрос.")
```

Техническая ошибка уже выводится в Console, а пользователь получает понятное сообщение без стека вызовов.

### 4.3 — Проверьте два сценария

#### HTTP-ошибка

Временно замените путь в `API_URL`:

```text
/applications → /application
```

Обновите страницу и найдите в Network ответ `404`.

#### Сетевая ошибка

1. Верните правильный URL.
2. Остановите `json-server` через `Ctrl+C`.
3. Нажмите «Обновить».

В Network запрос не получит нормальный HTTP-ответ, но интерфейс все равно должен показать состояние ошибки.

После проверки снова запустите backend:

```bash
npm run dev
```

### Быстрая проверка блока 4

- статус `404` обрабатывается через `response.ok`;
- выключенный сервер попадает в `catch`;
- в обоих случаях пользователь видит понятный текст;
- после перезапуска сервера кнопка «Обновить» возвращает список;
- `finally` снова включает кнопку независимо от результата.

## Блок 5. Отправка заявки через `POST` — 10 минут

**Цель:** превратить данные формы в JSON-тело запроса и сохранить новый объект на сервере.

Работайте в обработчике `submit`.

### 5.1 — Соберите объект заявки

Создайте `FormData` и получите знакомые по занятию 1-5 значения:

```js
const formData = new FormData(applicationForm)

const application = {
  name: formData.get("name"),
  email: formData.get("email"),
  topic: formData.get("topic"),
  createdAt: new Date().toISOString(),
}
```

Не добавляйте `id`: учебный сервер создаст его сам.

### 5.2 — Настройте `POST`

Вызовите `fetch` со вторым аргументом:

```js
const response = await fetch(API_URL, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
  },
  body: JSON.stringify(application),
})
```

Сопоставьте части:

- `method` сообщает действие;
- `headers` описывает формат тела;
- `body` содержит JSON-строку.

### 5.3 — Проверьте ответ

Добавьте ту же проверку `response.ok`, что и для `GET`. При ошибке выбросьте `Error` со статусом.

### 5.4 — Прочитайте созданный объект

```js
const createdApplication = await response.json()
console.log("Создана заявка:", createdApplication)
```

Найдите созданный сервером `id`.

### 5.5 — Обновите интерфейс

После успешного ответа:

1. вызовите `applicationForm.reset()`;
2. покажите `Заявка #... сохранена` в `submitStatus`;
3. выполните `await loadApplications()`.

Теперь источник истины — сервер: после `POST` frontend заново получает актуальный список.

### Проверьте запрос в Network

Выберите `POST /applications` и найдите:

1. Request Method — `POST`;
2. Status Code — `201`;
3. Request Payload — данные формы;
4. Response — созданный объект с `id`.

Откройте `backend/db.json`: новая заявка должна появиться в массиве `applications`.

### Быстрая проверка блока 5

- браузерная HTML-валидация останавливает пустую форму;
- отправляется JSON, а не объект JavaScript;
- успешный `POST` возвращает статус `201`;
- сервер добавляет `id`;
- форма очищается только после успешного ответа;
- список обновляется через повторный `GET`;
- заявка сохраняется после перезагрузки страницы.

## Бонус A. Фильтрация через API — `+0,5 балла`

Добавьте над списком заявок фильтр по теме. Фильтрация должна выполняться **сервером**, а не методом `filter` на уже загруженном массиве.

### Требования

1. Добавьте в `index.html` элемент `select`:
   - «Все темы»;
   - «Городская мастерская»;
   - «Доступные интерфейсы»;
   - «Личный сайт-портфолио».
2. При выборе темы выполняйте новый `GET` с query-параметром:

```text
GET /applications?topic=Доступные интерфейсы
```

3. Для значения «Все темы» используйте обычный `/applications` без query-параметра.
4. Сохраняйте обработку `loading`, `empty`, `success` и `error`.
5. Покажите в Network, что при смене темы меняется именно URL запроса.

Можно построить адрес через `URL` и `searchParams` либо аккуратно сформировать строку самостоятельно.

### Проверка и баллы

- `+0,25` — API получает корректный query-параметр, что видно в Network;
- `+0,25` — список и состояния корректно обновляются при выборе темы и возврате к «Все темы».

Фильтрация только через `applications.filter(...)` баллов не приносит: цель задания — изменить HTTP-запрос.

## Бонус B. Удаление заявки — `+0,5 балла`

Добавьте в каждую карточку кнопку «Удалить» и свяжите ее с REST API.

### Требования

1. Кнопка должна знать `id` конкретной заявки.
2. По нажатию выполняйте запрос:

```text
DELETE /applications/:id
```

3. Дождитесь ответа и проверьте `response.ok`.
4. Только после успешного ответа снова вызовите `loadApplications()`.
5. При ошибке не удаляйте карточку молча: покажите понятное сообщение пользователю и оставьте техническую ошибку в Console.
6. Проверьте, что объект исчез и со страницы, и из `backend/db.json`.

Подтверждение через `confirm` допустимо, но не является обязательным.

### Проверка и баллы

- `+0,25` — отправляется `DELETE` на URL с правильным `id`, ответ проверяется через `response.ok`;
- `+0,25` — после успеха список обновляется с сервера, а ошибка имеет видимое состояние.

Удаление карточки только из DOM не засчитывается: после перезагрузки она не должна возвращаться.

## Бонус C. Редактирование заявки — `+1 балл`

Превратите форму создания в форму с двумя режимами: **создание** и **редактирование**. Это сложное задание: потребуется согласовать состояние интерфейса, URL, метод и тело запроса.

### Сценарий пользователя

1. У каждой карточки появляется кнопка «Редактировать».
2. По нажатию значения выбранной заявки попадают в форму.
3. Заголовок и кнопка формы показывают режим редактирования.
4. Отправка формы выполняет:

```text
PATCH /applications/:id
```

5. После успешного ответа форма очищается, возвращается в режим создания, а список заново загружается с API.
6. Пользователь может отменить редактирование отдельной кнопкой и вернуться к обычному `POST`.

### Технические ограничения

- храните `id` редактируемой заявки в переменной состояния;
- для `PATCH` передавайте `Content-Type: application/json` и JSON-тело;
- не отправляйте `id` внутри тела запроса;
- проверяйте `response.ok`;
- блокируйте кнопку формы на время запроса;
- при ошибке сохраняйте введенные значения и режим редактирования;
- не изменяйте `db.json` напрямую для демонстрации результата.

### Проверка и баллы

- `+0,25` — кнопка карточки включает режим редактирования и заполняет форму данными выбранного объекта;
- `+0,25` — отправляется корректный `PATCH /applications/:id` с JSON-телом;
- `+0,25` — реализованы ожидание, проверка ответа, ошибка и отмена редактирования;
- `+0,25` — после успеха данные повторно загружаются с API, сохраняются в `db.json` и переживают перезагрузку.

Использование `PUT` вместо `PATCH` нужно отдельно обосновать преподавателю. В рамках этого задания ожидается частичное изменение существующего ресурса.

Сначала сохраните обязательную часть отдельным коммитом. Затем сделайте по одному коммиту на каждый бонус, например:

```bash
git add .

git add .
git commit -m "Add delete application bonus"

git add .
git commit -m "Add edit application bonus"
```

На проверке покажите для каждого выполненного бонуса:

1. действие в интерфейсе;
2. соответствующий запрос во вкладке Network;
3. HTTP-метод, URL, статус и тело запроса или ответа;
4. итоговое состояние страницы и `db.json`.
